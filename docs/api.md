# HTTP API

<sub>[Back to the README](../README.md)</sub>

The endpoints the web app itself uses. They are not a stable public interface and can change between releases.

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/health` | Server health and version info |
| POST | `/api/jobs` | JSON `{url, stems?}` or multipart `file + stems` → `{job_id}` |
| GET | `/api/jobs` | List completed (library) jobs |
| GET | `/api/jobs/{id}` | Job state snapshot |
| GET | `/api/jobs/{id}/events` | SSE stream of job state |
| POST | `/api/jobs/{id}/cancel` | Terminate active subprocess and cancel job |
| PATCH | `/api/jobs/{id}/sections` | Save waveform section markers for a job |
| PATCH | `/api/jobs/{id}/timeline-tags` | Save the timeline markers for a job: JSON `{timeline_tags: [{id, name, time}]}`, the whole list, stored in time order (#1075) |
| GET | `/api/jobs/{id}/stems/{name}.wav` | Stream a single stem as the song stores it: WAV, or MP3 (`audio/mpeg`) for a song stored as MP3 (#783) |
| GET | `/api/jobs/{id}/stems/{name}.mp3` | A stem as MP3: the stored file for a song stored as MP3, else a cached transcode |
| GET | `/api/jobs/{id}/stems/all.zip` | The chosen stems (and takes) as one ZIP, named after the song. Query: `format`, `stems`, and the click options. `reaper=1` (default off) adds `<song>.rpp`, a REAPER project with one track per file in the zip (the click too), at the stems' sample rate and the beat grid's median tempo (120 without a grid), each file named relative to the project; the download is then named `<song>_reaper.zip`. Without it the zip is unchanged (#1071) |
| GET | `/api/jobs/{id}/video.mp4` | Mux the current mix with the source video (MP4 upload or YouTube) into an MP4 |
| DELETE | `/api/jobs/{id}` | Remove job dir from disk (terminal jobs only) |
| POST | `/api/jobs/{id}/transcription` | Transcribe stems of a finished song into notes. JSON `{stems?: [name, ...]}`; without `stems`, every stem the song has (a silent one is recorded as skipped). Each stem goes to the transcriber it is routed to (`transcription_routes` in `/api/config`). Answers when the run ends, with the job state; meanwhile the job reports `transcription: "running"` and fills in `transcription_stems` as each stem finishes. A stem that fails is reported there with a reason code and does not stop the others. `404` unless the job is done, `409` while a run, a vocal split or a stem fill is in progress, `422` naming a stem the song does not have, `501` with `transcription_reason: "unsupported_platform"` where transcription cannot run. A run that ends early (cancelled, stalled, crashed) answers `500` with `transcription_reason`; the song stays done and finished stems keep their notes. Stop it with `POST /api/jobs/{id}/cancel` |
| GET | `/api/jobs/{id}/transcription` | The notes as JSON, per stem: `{start, end, pitch, velocity}` in seconds as transcribed, or with `quantize=1` snapped to the song's beat grid, each note then also carrying `bar`, `beat`, `part`, `step` and `steps`. Query: `stems` (comma-separated, default every transcribed stem), `quantize`, `parts` (parts per beat: 1, 2, 3, 4, 6 or 8, default 4). Also `quantize_available` and the grid's `confidence`, `detector`, `bpm` and `edited`. Quantising is worked out per request from the stored notes and the current grid, so an edited grid needs no new run. `404` when nothing is transcribed, `409` with `transcription_reason: "no_beat_grid"` for `quantize=1` on a song without a grid |
| GET | `/api/jobs/{id}/transcription.mid` | The transcription as one Standard MIDI File, a track per stem named after it, drums on channel 10, named after the song. As played by default (a fixed 120 BPM used only as a ruler). With `quantize=1` the notes sit on the beat grid and the file carries a tempo event per beat and time signatures from the grid's bars, so it lines up with a DAW's bars and still plays in time with the audio; whatever precedes the first beat is a short lead-in bar. Query: `stems`, `quantize`, `parts`. Stems with no notes are left out |
| GET | `/api/jobs/{id}/transcription.musicxml` | The quantised transcription as a MusicXML score, a part per stem: bars and time signatures from the beat grid, a tempo marking, the detected key as the key signature, bass clef for bass, percussion notation for drums, ties across bar lines. The `guitar` and `bass` parts are two staves, from the song's tab choices: staff 1 is five-line notation with every note on it, and staff 2 is a tab staff (a `TAB` clef, and `<staff-details number="2">` with its lines, the tuning of each string and the capo) that a notation program shows as tablature when the file opens. The tab staff is one voice, with the rhythm the Notation view draws, and carries a `<technical>` `<string>` and `<fret>` on every note the tuning reaches (string 1 is the highest, frets count from the capo); a note with no place on the instrument is on the notation staff only, and the tab staff rests where nothing placed sounds. Query: `stems`, `parts`. `409` with `transcription_reason: "no_beat_grid"` on a song without a grid |
| GET | `/api/jobs/{id}/transcription.alphatex` | The quantised transcription as [alphaTex](https://alphatab.net/docs/alphatex/introduction), the text score the Notation view draws with alphaTab: a track per stem named after it, bars and time signatures from the beat grid, a tempo marking, the detected key, drums as percussion, and one `\sync` point per bar (plus one at the end) that pins each bar to its time in the song in milliseconds, so a cursor can follow the audio through a tempo that drifts. `guitar` and `bass` are staff notation, tablature or both, as the song's tab choices say, with a string and fret for every note the tuning reaches; a note it does not reach stays on the staff and is left off the tab. One voice per staff: notes that start together are a chord, and a chord ends where the next begins. Query: `stems` (comma-separated; default every transcribed stem with notes, voices first and drums last), `parts` (parts per beat: `1`, `2`, `3`, `4`, `6` or `8`; default `4`), `unplaced` and `format`. A fretted stem shown as both is one staff of notation and tab, unless some of its notes have no string and fret: with `unplaced=staff` (the default) it is then two staves, notation with every note and tab with the placed ones; with `unplaced=omit` those notes are left out and it stays one staff, the form a tab editor reads, which the view uses for its Guitar Pro file. `format=text` (the default) answers the text alone, `text/plain`. `format=json` answers `{job_id, parts, stems, available, polyphonic, bars, grid, tab, file_names, alphatex}`: `stems` are the tracks drawn, `file_names` is what each download of these stems is called (`midi_played`, `midi_quantised`, `musicxml`, and `guitar_pro` for a Guitar Pro file made from the text; all named after the song), `available` every stem that could be, `polyphonic` the drawn stems whose held notes may be shortened, `grid` the beat grid's `{confidence, detector, bpm, edited}`, `alphatex` the text, and `tab` has, for each fretted stem drawn, its `{preset, tuning, capo, display}` with `notes` (how many it has), `unplaced` (how many found no string and fret), `reasons` (`{out_of_range: n, too_many_notes: n}`, reasons with none left out) and `suggestion` (the preset tuning that reaches the most notes, when more than 5% are out of range and one does better, else `null`). Never cached. 409 with `transcription_reason: "no_beat_grid"` when the song has no beat grid; 404 when nothing is transcribed, a named stem is not, or every stem asked for is silent; 422 for another `parts`, `unplaced` or `format`. A Guitar Pro file is made from this text by alphaTab in the browser (`new alphaTab.exporter.Gp7Exporter().export(score)`), so a client without the view can produce one the same way |
| POST | `/api/jobs/{id}/transcription.gp` | Hold a Guitar Pro file for download. The body is the file's bytes, `Content-Type: application/octet-stream`. The Notation view makes the file itself and sends it here so that it can be saved like any other export: the desktop app saves only what it fetches from this server. Answers `{job_id, url, file_name, bytes}`: where to download it and what it is called (the song's name, `.gp`). One file is held per song, replaced by the next, outside the song's folder, and dropped after 10 minutes. 404 unless the song is finished; 413 over 4 MB; 415 for another content type; 422 when the body is not a Guitar Pro 7 file (a zip holding `Content/score.gpif`) |
| GET | `/api/jobs/{id}/transcription.gp` | The Guitar Pro file last held for this song, as an attachment named after the song. Never cached. 404 when none is waiting or the one held is older than 10 minutes: the file is made on demand by the view, not by this server |
| GET | `/api/jobs/{id}/transcription/tab` | The song's tablature choices for each fretted stem. `{job_id, stems: {guitar: {preset, tuning, capo, display}, bass: {...}}, presets, displays, max_capo, custom}`. `tuning` is the open-string MIDI pitches, lowest string first; `preset` names it (`custom` when it is none of the presets); `capo` is a fret, `0` for none; `display` is `score`, `tab` or `both`. A song never given any has `standard`, `0` and `both`. `presets` lists the tunings on offer per stem (guitar: `standard`, `drop_d`, `half_step_down`, `d_standard`, `open_g`, `dadgad`, `seven_string`; bass: `standard`, `drop_d`, `five_string`, `half_step_down`) and `custom` the limits of a typed-in tuning. Stored as `stems/transcription/tab.json`, beside the notes; reading the defaults writes nothing. 404 unless the song is finished |
| PATCH | `/api/jobs/{id}/transcription/tab` | Change tablature choices. JSON `{guitar?: {preset?, tuning?, capo?, display?}, bass?: {...}}`: `preset` is one of the tunings on offer, or `tuning` is 4 to 8 whole MIDI pitches from 12 to 96 (it becomes the preset it equals, else `custom`); `capo` is `0` to `12`; `display` is `score`, `tab` or `both`. Only what is sent changes. Answers like the GET. 422 with the reason in `detail`, and nothing saved, when any part is refused: an unknown stem or choice, a preset not on offer, `custom` without strings, a preset and a tuning that disagree, a tuning of the wrong size or range, a capo out of range. Runs no model: the next score and the next downloads are fingered for the new choices |
